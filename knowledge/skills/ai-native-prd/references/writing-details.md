# AI-Native PRD 写作详细规范

本文件是 SKILL.md 的补充知识，动笔写任何一份 PRD 前必须通读并照做。

## 0. 顶层口径扫描（动笔写 Feature 前必做）

在拆出 Feature PRD 前，先扫原始需求中的「顶层口径」：指**影响 ≥2 个模块或多数 Feature 的未定规则**，不是某单个 Feature 内部的细节。

典型顶层口径：

- 是否需要账号/登录体系？浏览端公开还是登录可见？
- 存在哪些用户角色 / 权限边界（管理员 / 运营 / 普通用户）？
- 产品范围口径（如采集哪些层级、覆盖哪些渠道）？
- 外部服务选型（LLM 供应商、通知渠道、是否用第三方 PaaS）？
- 合规要求（数据来源合法性、是否需脱敏/备案）？

判定规则：

- 口径未定且影响 ≥2 个模块 → 列入《顶层待确认问题清单》。
- 清单问题数 ≥ 3，或直接影响 Feature 怎么拆 → **先停下向用户提问拍板**，未拍板前只输出「模块规划 + 顶层待确认清单」，不落盘 README / Feature PRD。
- 用户拍板或明确说「按默认假设先写」→ 才继续，并把拍板结论回填为文档既定口径（标注「已确认」）。

## 1. 量化 OKR（模块 README 必写）

模块 README 必须定义「可量化的核心业务指标」，让 AI 能判断代码是否真的完成任务，而不是写「提高用户体验」这类模糊目标。

格式：一个模块 README 的「核心业务目标」节，每条必须含具体数值。

```markdown
## 2. 核心业务目标（成功的定义）

- 功能可用性：xxx
- 性能指标：xxx
- 准确性/成功率：xxx
- 并发/容量：xxx
```

反面示例（禁止）：

```markdown
- 让创建速度尽量快
- 查询要尽可能稳定
```

正面示例：

```markdown
## 2. 核心业务目标（成功的定义）

- 创建项目的 P50 响应时间 < 300ms，P99 < 1s
- 查询列表支持 50 条/页，分页响应 < 500ms
- 模块所有接口鉴权拦截率 100%（未登录请求必定返回 401）
- 级联删除（项目 → 画布 → 节点）正确率 100%，无孤儿数据
```

```markdown
## 2. 核心业务目标（成功的定义）

- 任务提交成功率 > 99%
- 任务状态轮询 P95 延迟 < 30s 返回最终结果
- 支持单用户同时提交 ≤ 3 个任务
- 错误信息可读率 100%（所有错误码必须有用户可理解的中文提示）
```

## 2. 业务实体与属性

每份 Feature PRD 的实体表必须写清：

- 字段名
- 类型：string / int / boolean / JSONB / datetime / enum / uuid（按项目实际技术栈替换）
- 必填 / 可选 / nullable
- 长度 / 格式 / 枚举 / 默认值
- 关系（外键、所属父实体）/ 索引 / 唯一性
- 备注（中文，解释字段业务含义）

```markdown
| 实体 | 字段 | 类型 | 必填 | 约束 | 备注 |
|---|---|---|---|---|---|
| Project | title | string | 是 | 1-255 字符 | 项目名称 |
| Project | description | string | 否 | 长文本 | 项目简介，可为空 |
| Project | owner_id | int | 是 | 外键 -> User, INDEX | 所有者用户 ID |
| Project | status | enum | 是 | active/archived/deleted | 项目状态 |
| Canvas | title | string(255) | 自动 | 默认 "主画布" | 根画布名称 |
| Canvas | project_id | int | 自动 | FK -> Project, INDEX | 所属项目 ID |
```

## 3. 行为动作链

必须写清每个动作的完整链路：角色 → 触发动作 → 前置条件 → 输入 → 请求/操作 → 校验 → 写入 → 副作用 → 响应 → 状态变化。

```text
角色：项目所有者(manager)
  -> 触发：点击“邀请成员”
    -> 输入：{ user_id: "123", role: "editor" }
      -> 校验：user_id 是否存在、是否已是成员、role 是否合法
        -> 写入：INSERT INTO project_member(project_id, user_id, role)
          -> 副作用：发送通知给被邀请者
            -> 响应：{ code: 200, data: { member_id, user_id, role } }
              -> 状态变化：项目 member_count +1
```

## 4. 场景矩阵（BDD 预埋）

在 PRD 中定义场景结构，不直接写完整 Gherkin——场景矩阵是 BDD 的上游。

```markdown
| 场景 | 类型 | 角色 | 前置条件 | 触发 | 输入 | 副作用 | 期望结果 | 状态码 | 错误码 | BDD 文件 |
|---|---|---|---|---|---|---|---|---|---|---|
| 创建成功 | Happy Path | 已登录用户 | Token 有效 | 提交表单 | 合法参数 | 写库 | 返回 ID | 201 | - | 创建项目.feature |
```

必须覆盖以下 8 类场景（可多不可少）：

| # | 场景类型 | 关注点 |
|---|---|---|
| 1 | Happy Path | 主流程成功返回 |
| 2 | 参数非法 | 缺字段、超长、格式错、枚举错 |
| 3 | 鉴权失败 | 未登录 / Token 过期 / Token 无效 |
| 4 | 越权访问 | 无资源权限、角色不匹配 |
| 5 | 状态非法 | 已删除/已归档/流程状态不允许当前操作 |
| 6 | 幂等 / 重复提交 | 同用户重复触发同一操作 |
| 7 | 并发冲突 | 两人同时修改同一资源 |
| 8 | 外部依赖失败 | 第三方服务 / AI / 队列 / 存储不可用 |

## 5. 拦截铁网（8 类）

每份 Feature PRD 必须给出拦截表，且每项写明确处理策略（拒绝 / 排队 / 降级 / 重试 / 忽略）。

```markdown
| 类型 | 场景 | 拦截条件 | 后端响应 | 错误码 | 前端表现 |
|---|---|---|---|---|---|
| 参数 | 名称超长 | name > 255 | 422 | ERROR_NAME_INVALID | 表单提示 |
| 鉴权 | 未登录 | Token 缺失 | 401 | - | 跳转登录 |
| 越权 | viewer 编辑 | role != manager/editor | 403 | - | 按钮置灰 |
| 状态 | 已删除再编辑 | deleted_at != null | 404 | - | 提示不存在 |
| 幂等 | 重复提交 | 同 user + 同 project | 400 | ERROR_DUPLICATE | 提示已存在 |
| 配额 | 超限创建 | count >= max | 429 | ERROR_QUOTA_EXCEEDED | 提示上限 |
| 并发 | 两人同改 | version 冲突 | 409 | ERROR_VERSION_CONFLICT | 提示刷新 |
| 外部依赖 | 上游超时 | 第三方无响应 | 503 | ERROR_UPSTREAM_TIMEOUT | 提示重试 |
```

## 6. 待确认问题

需求含糊不清处就地标注，交给用户拍板，禁止 AI 脑补：

```text
[待确认: 允许空内容吗？如果允许，后续处理如何做？]
[待确认: 分享链接 require_login=false 与 permission=edit 冲突，具体文案是什么？]
```

## 7. 不做范围

明确排除以下内容，防止越界实现：

- 用户提过但明确说「以后再做」的功能
- 容易想当然加的功能（自动保存、撤销重做、版本对比等）
- 不属于当前需求的技术实现细节（加缓存、换消息队列等）
